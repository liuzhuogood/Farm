一、关键结论

  • 能发：发布版 v2026.11.17-1 在 10.0.0.6 上的核心链路（服务可用 → 设备列表 → 投屏 → 触控/按键/文本 → 文件 → 大屏 → 依赖 → 重连 → 重启恢复）全部可用，未发现 panic、崩溃、数据错乱或设备掉线。
  • 不建议回滚：现有部署可以继续对外使用。
  • 上线前建议修：N1（不存在的设备返回 ready，会误导 AI/自动化调用方）和 N2（/api/rotate 无效且会关掉用户自动旋转、pkill 掉同机其他投屏会话），这两条对共用这台机器的多服务环境风险最大。
  • 一个测试环境事实：只能用 https 访问；http://IP 下卡片正常但投屏永远「重连中」——WebCodecs 要求安全上下文，与部署说明一致，不是服务端缺陷。

三、问题清单（按严重度）

建议改N1

/api/v1/device-status 对不存在的设备返回 200 + status=ready

复现curl -sk "https://10.0.0.6:18080/api/v1/device-status?serial=no-such-device"
实际返回 {"status":"ready","width":0,"height":0}；/api/device-state/no-such-device 也返回 200（device_info.status=offline）
预期4xx，或 status 不为 ready
分析internal/automation/service.go: GetDeviceStatus() 固定置 Status:"ready"，wm size 失败时只是宽高为 0，不报错。AI 自动化调用方会把离线设备判成可用。
建议改N2

/api/rotate 不生效，且带两个副作用

复现连续调用两次 GET /api/rotate?serial=31040209940025Z，同时读 dumpsys window displays | grep cur= 与 settings get system accelerometer_rotation/user_rotation
实际user_rotation 0→1→0 已写入，但显示方向始终未变（cur 仍是 1080x2400）；accelerometer_rotation 被永久置 0；调用时会 pkill -f scrcpy
预期设备显示方向随调用切换；不应改变用户自动旋转设置；不应杀掉同机其他投屏会话
分析对照实验：同一台设备在可旋转应用（浏览器）里执行 wm user-rotation lock 1 能真正转成 2400x1080，说明设备支持旋转。而 /api/rotate 只写 settings，在 vivo V2072A / Redmi 上都不生效。pkill -f scrcpy 会打断这台机器上 mywebscrcpy 等共用同一批设备的投屏会话。
建议改N3

播放器「横竖屏」状态提示不可信

复现在可旋转应用（浏览器）里打开投屏，点一次工具栏「横竖屏」，观察状态提示与设备 dumpsys window displays | grep cur=
实际提示「已切换方向」，但设备仍是 2400x1080 横屏，画面尺寸也未变
预期提示与实际一致
分析usePlayer.ts rotate() 在 1.2s 后只比较 videoSize，重连抖动会让它误判成功。竖屏锁定应用里提示「应用可能锁定方向」是对的。
可带病上线N4

/api/ui/xml 对息屏设备返回 422，错误信息无法区分原因

复现让设备息屏，curl -sk "https://10.0.0.6:18080/api/ui/xml?serial=10.0.0.244:5555"
实际反复返回 422 {"error":"invalid_ui_xml"}；设备侧 uiautomator dump 报 ERROR: null root node returned by UiTestAutomationBridge
预期错误信息应能区分「设备息屏 / 无根节点 / XML 解析失败」，便于调用方决定是否先唤醒
分析亮屏设备（31040209940025Z、10.0.0.104）同一接口 200 正常返回 XML。
可带病上线N5

文件管理页不带 serial 时永久加载中

复现浏览器直接打开 /files（不带 serial 参数）
实际页面一直「正在加载文件」，顶部「容量信息不可用」，无任何提示或设备选择入口
预期提示先选择设备，或自动跳到上次使用的设备
分析带 /files?serial=10.0.0.30:5555 时正常列出 59 项、显示「已使用 23 GB / 47 GB」。
可带病上线N6

默认投屏参数偏低，1080x2400 机型只输出 448x1024

复现首次连接 wss://…/ws?serial=…（不带 quality 参数），读 meta
实际meta 为 448x1024（max_size=1024 / 15fps / 2Mbps），约原生的 43%；&quality=100 或首页画质调到 100% 后为原生尺寸
预期默认画质应接近机型原生，或首次进入时提示可调
分析internal/scrcpy/server.go DefaultConfig() 固定 MaxSize=1024、MaxFPS=15、BitRate=2M。息屏设备输出 AOD 尺寸 448x1024（比例 0.4375），与原生 0.45 差约 3%，大屏监控里格子高度因此不齐（428px vs 439px）。
观察O1

日志被外部 TLS 探测刷屏

复现tail -f /home/liuzhuo/farm/logs/farm.log
实际每 2 秒左右一条 http: TLS handshake error from 10.0.0.1:xxxxx: remote error: tls: unknown certificate，短时间内上千条
预期有效日志不被淹没（限流或单独归类）
分析10.0.0.1 侧有客户端持续用错误证书方式探测 18080，排查其它问题时会盖住有用日志。
观察O2

客户端断开后服务端仍保留推流会话

复现curl 连一次 /ws 后断开，再 ps -eo args | grep scrcpy.Server
实际断开 20 秒以上仍能看到该设备的 scrcpy server 进程在跑（15:43 那次残留了 20 分钟）
预期无人观看时释放，或明确保活时长
分析长时间占用设备与主机资源；多用户场景下容易互相抢会话。
